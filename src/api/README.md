# API + UI (Phase 10)

```
docker compose up -d db
DATABASE_URL="postgresql+psycopg://banking:banking@localhost:5433/banking_ai" \
  uv run alembic upgrade head
DATABASE_URL="postgresql+psycopg://banking:banking@localhost:5433/banking_ai" \
  uv run uvicorn src.api.main:app --reload --port 8080
# then open http://localhost:8080/
```

The first live consumer of Phases 6-9's orchestration/policy engine over HTTP — until now,
`run_golden_cases.py` and `live_case.py` were the only ways to exercise it. Every write endpoint
here calls the exact same functions those CLI scripts call
(`src.orchestration.live_case.create_and_run_case`, `src.policies.gateway.
approve_pending_action`) — this is a thin HTTP/HTML adapter, not a second implementation.

## Modules

- `main.py` — `create_app()`: mounts `cases.py`'s JSON router, `ui.py`'s HTML router, and
  `/static/`.
- `deps.py` — `get_db_engine`, and the **trusted-test-identity abstraction**
  (`docs/security-model.md` § 3: a real identity system is explicitly out of scope for this
  prototype). A `role` cookie, set via `POST /api/v1/cases/session` or `GET /session/{role}`
  (never a client-supplied request-body field for the endpoints it gates), stands in for a
  session. `require_reviewer_role` raises a real 403 for `customer`.
- `schemas.py` — every request/response body, `extra="forbid"`. Two response shapes for a case
  on purpose: `CustomerCaseView` (status + plain-language explanation only — no risk score, no
  evidence identifiers, `.claude/rules/frontend.md`) vs `AnalystCaseView` (everything). Which
  one a request gets is decided server-side by role, never by a client flag.
- `cases.py` — the JSON API (`docs/api-contracts.md` § 1). `GET /cases/{case_id}`'s analyst
  path re-derives evidence contradictions live via `detect_contradictions()` (the same function
  Phase 5/6/7 use) from the persisted `evidence` rows, rather than needing a separate
  contradictions table — one code path for computing contradictions, not two.
- `ui.py` — server-rendered HTML. Every route calls `cases.py`'s own request-handling functions
  directly in Python, overriding their `Depends(...)` defaults with real values — the same
  function, not a duplicate, builds both the JSON response and the page.
- `templates/*.html` (Jinja2) + `static/style.css`, `static/app.js` (vanilla, no framework) —
  see `docs/architecture.md` § 15 for why this resolves the frontend-framework `OPEN QUESTION`
  this way (server-rendered, no Node/npm toolchain).

## Frontend framework decision

Server-rendered Jinja2 + vanilla JS, not a SPA framework. The development machine is
memory-constrained (`docs/project-status.md` § Known limitations, hit repeatedly across
earlier phases); adding a Node/npm build step alongside Docker, Postgres, and the ML pipeline
buys a prototype at this scope nothing a second view-layer language wouldn't also cost in
complexity. `docs/architecture.md` § 15 records this as the resolution, not a placeholder.

## What was built

- **Three views**: a customer status page (`/customer/cases/{id}`), an analyst review queue
  (`/analyst/cases`), and the analyst case detail — the evidence graph, dual (customer/analyst)
  explanation, audit trail timeline, and approve/reject controls (`/analyst/cases/{id}`) —
  `prompt.md` § 36 calls this last one the project's visual centerpiece, prioritized per
  `docs/implementation-roadmap.md` Phase 10's own risk note.
- **Evidence graph visualization**: four genuinely distinct badge states (green
  `supports_legitimate`, red `supports_fraud`, gray `neutral`/`unknown`) plus a visually
  separate orange contradiction box connecting the two conflicting evidence IDs — never shades
  of the same color implying a spectrum (`.claude/rules/frontend.md`).
- **Role gating enforced server-side, twice**: both the JSON API (`require_reviewer_role` ->
  403) and the HTML routes independently apply the same dependency — a customer navigating
  directly to `/analyst/cases/{id}` gets the same 403 a script hitting the JSON endpoint would,
  not just a hidden link (`.claude/rules/frontend.md`: "never conditionally hidden-but-reachable
  for a customer session").
- **A real, previously-undiscovered persistence gap found and fixed**: `CaseExplanation.
  customer_explanation_es` (generated by the LLM client since Phase 6) was never persisted
  anywhere — only `analyst_explanation` reached the `decisions` table. Nothing surfaced this
  until Phase 10 needed to *read it back* for the customer view. Fixed by splitting
  `decisions.explanation` into `analyst_explanation` + `customer_explanation_es` (a migration,
  with existing rows backfilled into `analyst_explanation` rather than silently dropped —
  `.claude/rules/database.md`: "never a destructive migration without an explicit rollback
  path").
- **Executive dashboard: not built, by explicit scope decision.**
  `docs/implementation-roadmap.md` Phase 10 leaves it as `OPEN QUESTION` whether to build one at
  all (`docs/product-requirements.md` § 14) and its own risk note says prioritize the analyst
  evidence-graph view over anything else — that's what happened here.

## Verified (2026-09-27)

**Live, end-to-end, via curl**: `POST /api/v1/cases` against a real transaction built a real
evidence graph and persisted a real Decision; `GET /api/v1/cases/{id}` returned the full
evidence graph, dual explanation, and audit trail as an analyst, and only status + the
customer-facing explanation as a customer; a customer session got a real 403 on both the review
queue and the review endpoint; `POST /cases/{id}/review` approved a pending case and correctly
rejected an immediate resubmission (`no_pending_review`, 409) with the case's `human_review_status`
transition itself acting as a first layer of duplicate protection, ahead of the idempotency-key
check inside `approve_pending_action` (Phase 9) — the two layers guard different failure modes:
the status check gives a fast, clear rejection for a sequential retry; the idempotency-key
`INSERT ... ON CONFLICT` is what actually holds under a true concurrent double-submission (a
check-then-act status read alone has a race a concurrent request could still slip through).

**Live, end-to-end, in a real browser** (`.claude/rules/frontend.md`: "start the dev server and
exercise the golden path... in a real browser"): home page -> create a case by transaction ID ->
redirected straight to the analyst case detail -> evidence graph rendered with real data,
including two real contradictions from a genuinely mixed-evidence transaction, visually
distinct from the non-contradicting items -> dual explanation panel showing both the Spanish
customer text and the technical analyst text -> audit trail timeline -> switched to a case with
a pending review, clicked Approve, page reloaded showing `status: resolved` and the review
controls correctly gone. Also verified: role switcher moves between customer/analyst/supervisor
and the analyst queue link only appears for reviewer roles; the customer view of the same case
shows only status and plain-language text.

18 new automated tests (`tests/unit/test_api_cases.py`) — role-gating (403s), request
validation (`extra="forbid"`, invalid enum values), and 404s, run offline against an in-memory
SQLite engine (`StaticPool`, since the API opens/closes a connection per query rather than
holding one session — a plain `sqlite:///:memory:` engine would otherwise hand back a *fresh*
empty database on each connection). Full create/evidence-graph/review round trips need a real
Postgres — like `src/policies/gateway.py`/`src/evidence/persist.py` before it, verified live
above, not mocked in the test suite.

## Known, honestly-reported gaps

- **Correlation IDs are not yet propagated into audit events.** `src/api/main.py`'s middleware
  generates/propagates one per HTTP request, but `src/policies/gateway.py` and
  `src/evidence/persist.py` still always write `correlation_id=None` — they were built before
  any HTTP entry point existed to source one from. `docs/api-contracts.md` § 2 now states this
  gap explicitly rather than claiming the requirement is met.
- **No per-customer case-ownership scoping.** `docs/api-contracts.md` § 2's "a customer session
  can only read/act on their own cases" isn't enforced — the trusted-test-identity abstraction
  has a role, not a customer identity, so there's nothing to scope by yet. Any case_id is
  readable by any customer-role session today.
- **No live customer chat/message intake.** `POST /cases/{id}/messages` (the proposed endpoint
  for a customer to add a new message to an existing case) isn't built — `customer_message` for
  a case still comes from whatever `call_transcripts` row already exists
  (`src/orchestration/live_case.py`, Phase 6), not from someone typing in this UI. The customer
  view here is real-time *status*, not a chat widget capable of driving a new orchestration
  turn.
- **Rate limiting** (`docs/api-contracts.md` § 2): still `PLANNED`, not built.
- **Response schemas are FastAPI/Pydantic-generated OpenAPI** (`/docs`, `/openapi.json`,
  auto-enabled) — no hand-maintained duplicate schema doc, per `docs/api-contracts.md` § 2's own
  stated preference; not manually reviewed for polish beyond what FastAPI generates by default.
